Parallelization and Distributed Computing Plan¶

How multioutreg will spend less wall-clock time per run: first by removing work it does not need to do, then by running the remaining independent fits in parallel, and finally by moving heavy jobs off the web app onto more compute. The public GUI runs on Streamlit Community Cloud (multioutreg.streamlit.app), so most of this page is about getting the best out of a small, shared container. The last sections cover what more compute would unlock.

Goals and Non-Goals¶

Goals

  1. Every GUI page finishes a typical run (≤ 2 000 rows, ≤ 10 inputs, ≤ 5 outputs) on Streamlit Community Cloud without hitting the resource limits.

  2. One place to control parallelism (n_jobs), so library code, the CLI and the GUI all respect the same CPU and memory budget.

  3. Parallel results are identical to serial results for the same seed.

  4. A clear path to bigger hardware (workstation, cloud VM, GPU, cluster) without rewriting the model-selection code.

Non-goals (for now)

  • Multi-node training of a single model (data-parallel neural nets, distributed GP solvers).

  • A paid hosting migration. Hosting alternatives are listed so the decision can be made later.

  • Real-time multi-user scaling of the public demo beyond what Community Cloud provides.

Fix first: the Grid Search page selects twice¶

gui/Grid_Search_Surrogate_Models.py contains a duplicated block. After select_per_target picks a model on a validation split (line ~437), the page runs the following again (lines ~461–590):

  1. PCA a second time on inputs that were already PCA-transformed (line ~467).

  2. A Cartesian search over every combination of configs across outputs (ParameterGrid({"combos": [configs] * n_outputs}), line ~547). It scores each combination on the test set and overwrites the first result.

The second search grows exponentially with the number of outputs. It also undoes the leakage fix that select_per_target was written for. Deleting the duplicated block is the largest runtime win on this page, and it is a correctness fix as well.

Plan for Streamlit Community Cloud¶

With at most 2 cores, the order of the work matters: remove work, then cache, then parallelize at one level.

Phase 2: One parallelism setting, used everywhere¶

Add multioutreg/utils/parallel.py with a single source of truth:

and a context manager that caps native thread pools inside parallel regions:

with parallel_region(n_jobs) as n:     # threadpoolctl.threadpool_limits(1) for BLAS/OpenMP

Rules

  • Parallelize at one level only. When the outer loop is parallel, inner estimators get n_jobs=1 and native thread pools are capped at 1.

  • Default to the threading backend on Community Cloud. Use loky only where profiling shows the GIL is the bottleneck, and only once Phase 0’s lazy imports keep each worker small.

  • Keep results reproducible: derive every task’s seed from the parent seed (np.random.SeedSequence(seed).spawn(n)), never from worker order.

  • Keep the macOS OpenMP rule: set OMP_NUM_THREADS=1 and import lightgbm before other OpenMP libraries in tests and workers.

Because Phase 2 routes every loop through joblib.Parallel, moving to a Dask or Ray cluster is mostly a backend switch (with joblib.parallel_config(backend="ray")) rather than a rewrite.

Testing¶

  • Equality: for each parallelized function, n_jobs=1 and n_jobs=2 give the same chosen models, scores and predictions for a fixed seed.

  • Thread caps: a test asserts that BLAS/OpenMP pools are limited to 1 inside parallel_region (via threadpoolctl.threadpool_info()).

  • Memory: a smoke test runs the default Grid Search on the benchmark dataset under a 2.5 GB limit (e.g. ulimit -v or a container limit in CI).

  • No n_jobs=-1 in library code: a lint/grep check, so new code goes through get_n_jobs().

Open Questions¶

  1. Should the hosted app expose an “advanced compute” switch that is disabled on Community Cloud and enabled when MULTIOUTREG_N_JOBS is set?

  2. Which page is the priority for a background-job version: Grid Search, Auto-detect or Multi-fidelity?

  3. Is there a budget for a small always-on VM, or should heavy runs stay local (CLI) and the hosted app remain a demo?
