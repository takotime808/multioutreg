Proposal · HTML surrogate report

Lead with the answer, then show the evidence beside it

Today's report (multioutreg/report/template.html) is complete but hard to act on. It is ordered by analysis method, so a reader has to assemble the answer to "can I use this model for output X?" from six sections and a dozen stacked images. This proposal reorders the same content around the questions a user brings, puts a verdict on the first screen, and pairs every finding with the figure that proves it.

What gets in the way today

No answer up front

The Overview lists model type, levels and outputs. The generated Summary is a plain bullet list. Nothing states whether the model is fit for use, or for which outputs.

Overview, Summary

Ordered by method, not by question

Metrics tables, then UQ plots, conformal, predictions, SHAP, PDP, sampling, diagnostics. Judging one output means visiting every section.

section order

Findings far from evidence

"The 95% interval covers only 74% of test points" sits in Summary. The coverage plot that shows it is several screens down, with a generic caption.

summary_points vs uncertainty_plots

Numbers without a reference

An R² of 0.81 or a coverage of 0.91 means little alone. Targets, the HF-only baseline and sampling-noise bands live in other tables or are missing.

Regression / Uncertainty Metrics

One 800px image after another

Every figure is a full-width PNG in a single column. Outputs can't be compared side by side and axes aren't shared. SHAP and PDP add one image per output, so 6 outputs means 12 large images.

.plot { max-width: 800px }

Gaps look like failures

An optional analysis that didn't run shows a red "plot is unavailable" message. The reader can't tell a bug from a skipped step.

Ideas

1

A verdict and a scorecard on page one

One sentence that says which outputs are ready, then an outputs × criteria matrix (accuracy, error bars, multi-fidelity gain) with pass / caution / fail chips. Every rule uses values the GUI already computes (r2, empirical coverage, rmse_change_pct), and the thresholds are printed in the appendix so the verdict is auditable.

See mockup A
2

Findings as claim + evidence cards

Turn each _summary_points string into a card: the claim as the heading, a status, one small chart that proves it, and a link to the full section. The headline of each chart is the finding, not the chart type ("CD's error bars are too narrow", not "Coverage Plot").

See mockup A
3

A "what to do next" list

Turn diagnoses into actions: report conformal intervals for CD, add high-fidelity runs where predicted std is largest (the active module can pick them), drop a level that carries no information, consider the simpler HF-only model when MF gives no gain.

See mockup A
4

Every number gets a reference

Show each metric next to its target, its baseline or its noise band: coverage with the ±1.96 binomial band for the test-set size, RMSE as a % of the HF-only model, CV scores with fold spread so "statistically tied" candidates are visible.

See mockup B
5

Per-output blocks of small multiples

Parity, residuals, error histogram and ordered intervals for one output in a 2×2 grid with a stat strip on top, switchable by output. Each output keeps one color across every figure in the report.

See mockup B
6

Captions that say what to look for, and annotations on the plot

Replace the italic boilerplate with a one-line "look for" and draw the computed finding onto the chart itself, for example the residual slope and whether it is significant, or the points that fall outside their interval.

See mockup B
7

One chart where there were three

Overlay Gaussian and conformal coverage on one calibration chart per output, with the sampling-noise band drawn around the diagonal. Today they are in separate sections with separate captions.

See mockup C
8

Chart forms chosen for the question

A dumbbell for MF vs HF-only, an r vs R² quadrant for "is this fidelity level informative or just biased?", a feature × output SHAP heatmap in place of one beeswarm per output, and a PDP grid with shared axes.

See mockup D
9

Navigation and provenance

A sticky section index, a run header (model, data hash, seed, package version, date), and a collapsed appendix that holds the raw tables. Optional steps that didn't run become a grey "skipped: reason" line, not a red error.

See mockup D

Example pages

All four use one synthetic run: a 3-level multi-fidelity surrogate of a wing section (panel method, coarse RANS, fine RANS) predicting CL, CD and Cm. The numbers are made up but consistent across pages, and the verdict and chips are computed from them by the rules described on each page.

How to get there, cheapest step first

  1. Template only. Reorder sections in template.html, add CSS grid so figures sit two or three across, add the sticky index, style the Summary, and swap .errormsg for a "skipped" line. No Python changes; all three report callers (pages 01 and 02, grid_search_core.py) pick it up.
  2. Verdict and scorecard. Add a verdict(metrics, uncertainty_metrics, baseline_rows, n_test, thresholds) helper next to _summary_points, ideally moved into multioutreg/report/ so every caller shares it. Return structured findings (claim, status, section, plot_key) instead of strings.
  3. New figures. Add the dumbbell, level quadrant, calibration overlay, SHAP heatmap and CV dot plot to multioutreg/figures/, each returning the same {img_b64, title, caption} dict the template already renders. Emitting SVG instead of PNG keeps text crisp and files smaller.
  4. Fixed output colors and shared axes. Pass one output→color map through every plotting call so an output looks the same everywhere.
  5. Optional interactivity. Embed the per-output block's data as JSON and draw it client-side (as these mockups do) so readers can switch outputs and hover points without regenerating the report.

    4 · Did the low-fidelity data help?

    Test RMSE of the multi-fidelity model, indexed to the same base model trained on high-fidelity data only (= 100%). Outputs have different units, so indexing puts them on one axis.

    HF-only baselineMulti-fidelity modelwithin ±5%: no clear gain

    Which lower levels carry information?

    Read: correlation r of a model trained on that level alone with the high-fidelity truth (x) against its R² (y). High r with low R² means biased but informative, which multi-fidelity can correct.

    Data per level

    Read: how many runs each level contributed, and what one run costs.
    The Fidelity Levels table and the MF vs HF-only table become two charts that answer "did it help?" and "why?". The quadrant explains the dumbbell: f0 helps CL because it tracks CL closely despite its bias, and does nothing for CD because it doesn't track CD at all.
    5 · What drives the outputs?

    Angle of attack dominates CL and Cm; Mach number dominates CD

    Share of mean |SHAP| per output (each column sums to 100%). One heatmap replaces one SHAP image per output.

    How the top three inputs move each output

    Partial dependence with the 10th–90th percentile of individual curves. Columns share an x axis, rows share a y axis.

    The heatmap shows the ranking for every output in one glance and scales to many outputs. The PDP grid lines up the same input across outputs, which makes the drag rise near Mach 0.78 stand out against the flat CL and Cm curves.

    7 · How was the model chosen?

    5-fold CV RMSE on the high-fidelity training rows, averaged over outputs after scaling each by its std. Whiskers span ±1 std across folds. The test set was not used for selection.

    A ranked table hides that the top candidates overlap. Fold spread makes it visible, and the "tied" chips tell a reader that choosing the simpler of the tied models would be reasonable.
